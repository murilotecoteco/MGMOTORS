O maior problema encontrado **não é funcional, é de permissão no banco**: a view pública `usuarios_publicos` está gravável por `anon` e `authenticated`. Isso permite alterar ou excluir o perfil de qualquer usuário usando apenas a chave pública do site. É um **P0** e deve ser corrigido antes de qualquer outra melhoria.

Depois do P0, as frentes com maior retorno são:

1. privacidade/LGPD (Chatling antes do consentimento);
2. proteção dos formulários públicos;
3. SEO (Open Graph, JSON-LD, página de anúncio);
4. testes E2E e acessibilidade;
5. performance (`/api/config`, `auth.getUser()` em toda página, fontes, upload de imagens).

## 3. P0 — Escrita anônima na view `usuarios_publicos`

### 3.1 O que acontece

A view `public.usuarios_publicos` é recriada em `supabase/migrations/20261008000000_legal_consent.sql` com:

```sql
DROP VIEW IF EXISTS public.usuarios_publicos;
CREATE VIEW public.usuarios_publicos AS
SELECT id, nome, foto, capa_foto, cidade, estado, bio, site, instagram,
       seguidores, seguindo, nota_media, total_avaliacoes, criado_em
FROM public.usuarios;
```

O projeto Supabase tem *default privileges* que concedem `ALL` em tabelas/views a `anon`:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public"
  GRANT ALL ON TABLES TO "anon";
```

A migration seguinte faz apenas `GRANT SELECT`, **sem revogar** INSERT/UPDATE/DELETE. O snapshot de produção confirma:

```sql
GRANT ALL ON TABLE "public"."usuarios_publicos" TO "anon";
GRANT ALL ON TABLE "public"."usuarios_publicos" TO "authenticated";
```

Como a view é um `SELECT` simples de uma única tabela, ela é **auto-atualizável**. Um `UPDATE`/`DELETE` na view é redirecionado para `public.usuarios` e executado com os privilégios do dono (`postgres`), **ignorando o RLS da tabela base**.

### 3.2 Evidência

Teste **não destrutivo**, com filtro para um UUID inexistente:

```text
GET    /rest/v1/usuarios_publicos?select=id&limit=1   → 200
PATCH  /rest/v1/usuarios_publicos?id=eq.00000000-0000-0000-0000-000000000000 → 204
DELETE /rest/v1/usuarios_publicos?id=eq.00000000-0000-0000-0000-000000000000 → 204
```

O `204` em PATCH e DELETE confirma que o PostgREST aceita escrita na view. Nenhuma linha foi alterada porque o UUID não existe.

### 3.3 Impacto

Com um `id` real, um atacante com a chave publishable/anon (que é pública e entregue por `/api/config`) poderia:

- alterar `nome`, `foto`, `capa_foto`, `bio`, `cidade`, `estado`, `site`, `instagram`, `seguidores`, `seguindo`, `nota_media` e `total_avaliacoes` de qualquer usuário;
- **excluir o perfil de qualquer usuário**, com cascata para anúncios, mensagens, seguidores e avaliações;
- personificar visualmente outro usuário (nome/foto/bio), facilitando golpes;
- inflar métricas públicas (seguidores, nota média).

Não é possível alterar `email`, `is_admin` ou `banido` por essa view, porque essas colunas não são expostas. Ainda assim, o impacto de integridade e disponibilidade é crítico.

> A auditoria anterior de RLS não detectou porque o script testa tabelas, não views. Vale incluir views e default privileges no checklist.

### 3.4 Correção sugerida

Criar uma nova migration, por exemplo `20261103000000_fix_usuarios_publicos_privileges.sql`:

```sql
-- A view é somente leitura para o público.
-- Sem isso, o GRANT ALL herdado das default privileges permite
-- UPDATE/DELETE em public.usuarios via view auto-atualizável.
REVOKE ALL ON TABLE public.usuarios_publicos FROM anon, authenticated;
GRANT SELECT ON TABLE public.usuarios_publicos TO anon, authenticated;
GRANT SELECT ON TABLE public.usuarios_publicos TO service_role;

DO $$
BEGIN
  IF has_table_privilege('anon', 'public.usuarios_publicos', 'INSERT')
     OR has_table_privilege('anon', 'public.usuarios_publicos', 'UPDATE')
     OR has_table_privilege('anon', 'public.usuarios_publicos', 'DELETE') THEN
    RAISE EXCEPTION 'hardening falhou: anon ainda pode escrever em usuarios_publicos';
  END IF;

  IF has_table_privilege('authenticated', 'public.usuarios_publicos', 'INSERT')
     OR has_table_privilege('authenticated', 'public.usuarios_publicos', 'UPDATE')
     OR has_table_privilege('authenticated', 'public.usuarios_publicos', 'DELETE') THEN
    RAISE EXCEPTION 'hardening falhou: authenticated ainda pode escrever em usuarios_publicos';
  END IF;
END $$;
```

Adicionar a mesma verificação em:

- `supabase/tests/verificar-hardening.sql`;
- `supabase/tests/rls-security-check.sh`;
- checklist de `PROXIMOS-PASSOS-20261022.md`.

### 3.5 Verificação segura

```sql
-- Deve retornar false, false, false após a correção
select
  has_table_privilege('anon', 'public.usuarios_publicos', 'INSERT') as insert,
  has_table_privilege('anon', 'public.usuarios_publicos', 'UPDATE') as update,
  has_table_privilege('anon', 'public.usuarios_publicos', 'DELETE') as delete;
```

### 4.2 Sobre o consentimento

O banner de termos (`headerGlobal.js`, função `mostrarBannerTermos`) grava `mg_termos_aceitos` no `localStorage` para visitantes. Isso **não é um registro de consentimento**: some ao limpar o navegador, não tem versão, não tem data e não é auditável. Para usuários autenticados, o aceite é registrado corretamente via `registrar_aceite_legal`.

Sugestão:

- tratar o banner de visitante como **aviso informativo**, não como consentimento legal;
- registrar o aceite anônimo no servidor (com política de INSERT adequada) ou remover a promessa de "aceite";
- carregar Chatling apenas depois do aceite;
- incluir na Política de Privacidade a lista de operadores: Supabase, Vercel, Chatling, Google (OAuth).

### 4.3 Ponto positivo

O projeto já tem uma migration de hardening séria (`20261020120000_security_hardening.sql`) e um verificador com 27 PASS. O problema da view mostra que o hardening precisa cobrir **views e default privileges**, não só tabelas.

## 6. Performance

### 6.1 Medições em produção

| Recurso | Resultado |
|---|---|
| `/api/config` | **~1,04 s** (cold) para 121 bytes |
| `/api/carros-ia` | **~2,14 s** para 903 bytes |
| `marketplace.html` | ~0,50 s, 77 KB |

### 6.2 Pontos de atenção

1. **Toda página faz `fetch("/api/config")`** antes de inicializar. Isso adiciona um round trip de ~1 s em cold start. Cachear com `s-maxage` curto ou embutir a config no build.
2. **`carregarHeaderGlobal` chama `auth.getUser()` em toda página**, mesmo para visitante anônimo. Para a UI, `getSession()` local é suficiente; a validação real já é feita pelo RLS no servidor.
3. **A home faz 3 contagens exatas** (`anuncios`, `marcas`, `usuarios`) a cada visita (`MG-INICIO/inicio.html:301-309`). Cachear ou usar uma RPC agregada.
4. **Fontes via `@import` dentro de 20+ CSS** (Ruda). Isso é render-blocking e repetido. Melhor `<link rel="preconnect">` + um único `@font-face`/stylesheet, ou self-host.
5. **Chatling em 21 páginas** adiciona JS de terceiro em todas as telas. Carregar sob demanda.
6. **Upload sem compressão**: até 5 MB por foto, 5 fotos → 25 MB por anúncio. Redimensionar para ~1600 px e converter para WebP no cliente.
7. **Geolocalização no submit** (`marketplace.html:1155-1159`) pode travar o formulário por 3 s e pede permissão no pior momento. Melhor preencher a cidade por CEP ou tornar a localização opcional.
8. **Header injetado via JS** em todas as páginas. Um partial estático/pré-renderizado reduz CLS e evita header vazio se o módulo falhar.

### 6.3 Meta sugerida

- LCP < 2,5 s no 4G;
- CLS < 0,1;
- `/api/config` com cache e < 200 ms em warm;
- peso inicial da home < 500 KB sem imagens de anúncio.

Também vale consolidar os cinco documentos de análise em um único “estado atual” e manter os demais como histórico. O `INDICE-ANALISES.md` pode apontar para este documento como a análise mais recente.

## 11. Sugestões de produto

Depois de estabilizar segurança e documentação:

1. **Selo de vendedor verificado** (documento/telefone) — aumenta confiança e diferencia o marketplace.
2. **Buscas salvas + alertas** (“quero um Porsche até R$ 400k”) — retenção.
3. **Simulador de financiamento** — já está no roadmap e é uma objeção real de compra.
4. **Comparador de veículos** — útil no segmento premium.
5. **Anúncios em destaque** — modelo de monetização natural.
6. **Painel do vendedor** com visualizações, contatos e tempo médio de venda.
7. **Exportação de dados do usuário (LGPD)** — hoje há exclusão, mas não portabilidade.
8. **Observabilidade**: Sentry (ou similar) + Web Vitals + logs estruturados. Hoje os erros só vão para `console.error`.

## 14. Conclusão

O MGMOTORS tem uma base sólida e uma documentação acima da média para um projeto acadêmico. O que separa o projeto de um nível profissional agora não é adicionar funcionalidades, e sim:

1. **manter as migrations e o hardening verificados em produção**;
2. **executar o fluxo autenticado com contas de teste**;
3. **concluir a CSP sem `unsafe-inline`**;
4. **decidir retenção/exclusão das tabelas legadas**;
5. **finalizar Turnstile, Sentry e SEO dinâmico da página de anúncio**.

Com esses ajustes, a apresentação fica muito mais defensável: em vez de “o site tem muitas telas”, o discurso passa a ser “o site tem muitas telas, com permissões verificadas, testes reproduzíveis e limites conhecidos”.
